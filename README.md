# 接收抽样后端服务（OC 曲线 / 风险 / 方案设计 / GB/T 2828.1 检验流）

Go 1.23 + Echo + PostgreSQL 16 的纯 HTTP 后端，覆盖：

- **方案档管理**：一次 / 二次抽样档的新建、修改、删除、按名查询。
- **统计计算**：接收概率 Pa、二次抽样 ASN、带批量 N 时的 AOQ / AOQL / ATI、生产方风险 α 与使用方风险 β、OC 曲线。
- **反向设计**：按 (AQL, α, LTPD, β) 搜索最小样本量一次方案；二次方案限定 n2=n1 或 n2=2·n1，在可行方案中取 AQL 处 ASN 最小者。
- **检验流**：一条流绑定正常 / 加严 / 放宽三个档，逐批录入，按 GB/T 2828.1 转移规则推进严格度；补录、删改后逐字段与“从头重放”一致。

只提供 HTTP/JSON 接口，无前端。

## 2. 概率模型与对数域计算

- 带批量 `N`：**超几何分布**（不放回）；二次抽样第二阶段用条件超几何（抽走 n1 后，剩余批量 N−n1、剩余不合格品 K−d1）。
- 不带 `N`：**二项分布**。
- 显式 `distribution=poisson`：**泊松近似**，响应带 `"approximate": true`；当 `n·p > 5` 时在 `warnings` 中给警告。

所有组合数与概率都在**对数域**计算：

- `LogComb(n,k) = lgamma(n+1) − lgamma(k+1) − lgamma(n−k+1)`，`n` 到几千也不溢出；越界输入返回 `−Inf`，不可能事件永远不会“悄悄变 0”被计入概率质量。
- 概率求和用 `log-sum-exp`，仅在最后取一次指数；端点 `p=0`、`p=1` 给出**精确**的 1 / 0（三种分布一致）。

关键端点（测试可证）：

| 性质 | 结论 |
| --- | --- |
| p = 0 | Pa 恰为 1 |
| p = 1 且 c < n | Pa 恰为 0 |
| n 不变、c 增大 | 整条 Pa 曲线不下降 |
| c 不变、n 增大 | 0 < p < 1 处 Pa 下降 |
| N → ∞ | 超几何 Pa 单调逼近二项 |
| 二次退化为 n2=0, c1=c2, r1=c1+1 | 与对应一次方案**逐位相同** |
| 二次 ASN | 始终落在 [n1, n1+n2] |
| ATI | 始终落在 [n, N] |
| AOQL | 不小于曲线上任一点 AOQ |

### 手算核对例子：n = 80, c = 2（二项）

Pa(p) = Σₖ₌₀² C(80,k) pᵏ (1−p)^(80−k)：

- p = 0.01 → Pa ≈ **0.95345**（α ≈ 0.04655）
- p = 0.02 → Pa ≈ 0.78442
- p = 0.05 → Pa ≈ **0.23062**（若 AQL=1%、LTPD=5%，β ≈ 0.2306）
- p = 0 → 1；p = 1 → 0

## 3. 反向设计

**一次方案**：对固定 n，令

- `cMin(n)` = 使 Pa(AQL) ≥ 1−α 的最小 c；
- `cMax(n)` = 使 Pa(LTPD) ≤ β 的最大 c。

n 可行 ⇔ `cMin(n) ≤ cMax(n)`，该谓词随 n 单调，故用二分找最小 n；同 n 取最小 c。返回前由统一 OC 引擎复核风险。搜索上限默认 `n ≤ 2000`（硬上限 20000，可用 `n_max` 覆盖）；找不到明确返回 `404 no feasible plan`。测试证明：**n−1 时任何 c 都不再可行**。

**二次方案**：仅允许 n2 = n1（`equal`）或 n2 = 2·n1（`twice`）。利用“固定 c2、c1 时 Pa 与 P2 随 r1 单调”，对每个 (n1, c2, c1) 在 r1 上二分，取满足两风险约束的最小 r1（同时最小化 AQL 处 ASN），整体复杂度 O(n1²·log n1)。默认 n1 上限 200（硬上限 1000，`n1_max` 可调）。测试以内部前缀求值器对整个可行空间做暴力比对，确认全局 ASN 最优。

## 4. GB/T 2828.1 检验流转移规则

状态：`normal → tightened → reduced`，加严可 `suspended`（暂停检验，需人工恢复后以加严重新开始）。

- **正常 → 加严**：最近连续不超过 5 批中有 2 批不接收。
- **加严 → 正常**：连续 5 批接收（任一拒收清零连收计数）。
- **正常 → 放宽**：转移得分累计达到 30，**且**流上同时标记 `stable`（生产稳定）与 `approved`（主管同意）。
- **放宽 → 正常**：任一批不接收；或“生产稳定”标记被撤销（立即回正常）。
- **加严 → 暂停**：加严期间累计 5 批不接收。暂停后到达的批次记录为 `not_inspected`；人工 `resume` 后以加严重新计数。
- **转移得分（正常档）**：拒收清零；接收按 GB/T 2828.1 加分表——
  - c = 0：d = 0 加 2；
  - c = 1：d = 0 加 2、d = 1 加 1；
  - c ≥ 2：d ≤ c−2 加 3、d = c−1 加 2、d = c 加 1。
  - 二次抽样：一阶段接收按 c1、二阶段接收按合计 c2 查同一表。

每条批次记录都带：当时严格度 `severity`、所用方案 `plan_id/plan_name`、判定 `decision/accepted`、转移后 `score`、转移说明 `note`，以及判定该批所用方案的**修订号 `revision_no`**（暂停未检批为 `null`）。

## 4.1 方案档修订历史：改档即追加修订，判定按检验时刻取档

方案档不再只有“当前值”。每个档有一条**只增不改**的修订历史 `plan_revisions`：每次修改追加一个修订，带修订号（每档自 1 起连续）与**生效时刻** `effective_at`；已落地的修订永不变更，纠错只能再追加一个修订。

- **按检验时刻取档（含边界）**：判某一批时，该严格度槽位取“生效时刻 `<=` 批检验时刻”的最新修订；生效时刻**恰好等于**检验时间按**新**修订算；同一生效时刻并列时修订号大者胜。因此修订可以生效于将来，也可以补记到过去（可能插在两个已有修订之间）。修订 1 的生效时刻取可表示的最早时刻，**覆盖全部历史**，任何早于建档的补录都能落到它。
- **批次记录可见用的是哪个修订**：`batch_results.revision_no` 逐批落档，与从头重放一致；暂停期间的 `not_inspected` 批不查任何修订，该字段为空。
- **转移得分不另开特例**：得分加分取决于“该批当时生效修订”的接收数。正常检验中途换了修订，得分由 §4 的加分表对每一批自然续算——例如 c=2 下 d=0→+3、d=c−1→+2、d=c→+1，换成 c=1 后 d=0→+2、d=1→+1，拒收清零；重放时同一条连续序列穿过修订边界，分数平滑延续（见 §4.2 的 n=80 手算例与 `TestRevisionHistoryHandComputed`）。
- **老接口兼容**：`PUT /plans/{id}`（不带生效时刻）保留，语义变成“追加一个**即刻生效**的新修订”，不再原地覆盖、也不改写此前历史，老客户端不报错。

### 修订让已录批次无法判定 → 整次修订被拒，逐批指出冲突

追加修订前，事务内会把“追加后的完整修订历史”叠到每个绑定流上做一次**严格重放**：某批的不合格数超出它在“自身（严格度, 检验时刻）”所命中修订的样本量（如样本量改小、或二次抽样缺少必要的二阶段计数等），该批无法判定。此时**整次修订回滚**（一个修订行都不写、任何派生结果都不改），响应 `422` 并在 `conflicts` 里**逐批**给出 `batch_id / lot_no / inspected_at / severity / 计划档 / 命中的修订号 / 原因`，绝不把它悄悄当接收或拒收。修好这批后再次追加，可能继续暴露后续冲突（冲突清单沿一次确定性的连续重放给出）。

录批时的录入校验也按**该批检验时刻**三个槽位各自生效的修订进行，而不是拿当前最新修订去卡历史补录。

### 同步还是异步：选同步，理由与代价

**结论：追加修订与受影响流的重算放在同一个数据库事务里同步提交。** 流程为：取该档的事务级咨询锁 → 按 id 升序取所有绑定流的咨询锁 → 用“待定历史”严格重放逐流验冲突并留痕 → 插入修订行、更新 `plans` 当前镜像 → 在已持有的流锁内整流重放替换派生表 → 提交，并随响应返回**差异报告**（哪些流、哪几批的严格度/判定/得分/所用修订从什么变成什么；一批没变也明确给出 `changed:false`）。

理由：

1. **“任何时刻读到的流不许是新旧修订混判的半成品”是硬约束，同步在一个事务内天然满足。** 修订行与全部派生结果原子可见：提交前读家完全停留在追加之前，提交后整条已是按最新历史算好的样子。异步方案要达到同样保证，必须额外引入“追赶水位 + 整条流停写/标记 stale + 读侧回退”等一整套机制，并回答“追上之前读什么、差异去哪里取、追的途中又来了新修订怎么办”，复杂度与出错面都大得多。
2. **差异随操作同步返回，可直接核对。** 不需要额外的差异查询与保留策略；差异就是事务内“提交前派生快照 → 重放后快照”的逐字段 diff，和验收要求的“与重放前后实际对比吻合”是同一份计算。
3. **不产生活锁/死锁，也不彼此等死。** 加锁顺序恒为“档锁 → 流锁（按流 id 升序）”；录批事务只拿流锁，从不拿档锁，因此等待图无环。同一流的录批在修订事务期间排队，随后自然串行；**不同流互不阻塞**（咨询锁键随流不同）。并发压测（多客户端同时给同一档追加修订、同时往绑定流录批，外加死锁压力）验证：修订号不缺号、批次不丢、得分不重复累计，且每批命中的修订号与“生效时刻 ≤ 检验时刻的最新修订”逐行相符。

代价（已接受）：

- 一个档挂着多条很长的流时，追加修订会在一个事务内顺序重算它们并持有相应流锁到提交，写延迟随 Σ(各流批次数) 增长。与现有“每次增删改整流重放”一致，普通实例上数千批为亚毫秒~毫秒级；将来单流达到数万/数十万，再按 §5 已预留的检查点方向优化，不改变正确性模型。
- 录批请求与修订在同一流上串行，极端情况下录批要等修订重算完。换取的是零半成品读取与零异步对账，对本系统规模是正确的取舍。

### n=80、c=2 → c=1 手算例

正常档在时刻 T 由 n=80、c=2 改为 c=1（修订 2 生效于 T；修订 1 为 n=80、c=2）。各批按检验时刻取档：

| 批 | 检验时刻 | d | 命中修订 | 判定 | 转移后得分 |
| --- | --- | --- | --- | --- | --- |
| a | T 前 | 0 | 1（c=2，d≤c−2→+3） | 接收 | 3 |
| b | T 前 | 1 | 1（d=c−1→+2） | 接收 | 5 |
| c | T 前 | 2 | 1（d=c→+1） | 接收 | 6 |
| d | T 后 | 0 | 2（c=1，d=0→+2） | 接收 | 8 |
| e | T 后 | 1 | 2（d=1→+1） | 接收 | 9 |
| f | T 后 | 2 | 2（c=1，d=2 拒收→清零） | **拒收** | 0 |

修订前 f 在 c=2 下本是接收（得分 12）；追加修订后同一条序列重放，a/b/c 仍按修订 1（3/5/6），d/e/f 改按修订 2（8/9/拒收清零），差异报告点名 d/e/f 的修订变化与 f 的判定翻转。该例有领域层与端到端两层测试固定。

### 原地升级（拿旧版数据卷直接起新版）

`schema.sql` 幂等迁移：新建 `plan_revisions`、给 `batch_results` 增加 `revision_no`，然后为每个旧 `plans` 行补一个**覆盖全部历史的修订 1**（参数逐列照搬），并把已判定批的 `revision_no` 回填为 1、暂停未检批保持 `NULL`。流当前状态与每批的严格度/判定/得分等既有字段**逐字段不变**；反复重启不会多出修订（反重复插入只补缺的修订 1，回填只动仍为 NULL 的已判定行），也不会再改写数据。专项用例 `TestInPlaceMigrationFromLegacy` 先按升级前表结构灌入含转移/暂停历史的数据，升级后逐字段比对并二次迁移验证幂等。

## 5. 历史可改：为什么选择“整条重放”

**结论：每次增 / 删 / 改都在一个事务里把该流的事件按时间顺序从头完整重放，重算所有派生结果。**

事件表 `stream_events` 是唯一事实源（批次、标记变更、人工恢复），按 `(inspected_at, seq)` 全序排列；`seq` 是每流单调递增的分配序号，因此物理到达顺序与结果无关——补录更早的批、删批、改不合格数都只改变事实集合，重放结果是该集合的纯函数。派生表 `batch_results` 与流当前状态只是缓存，在同一事务内整体替换。

选择整条重放而不是“从被改批起增量 + 检查点”的理由：

1. **正确性边界太多，增量极易漏算。** 一次补录的拒收可能改变十几批之前的转移触发点，进而改变此后每一批“当时用哪个档判定”；转移得分清零、正常↔加严窗口滑动、放宽标记撤销、暂停区间（区间内批次为 not_inspected，恢复后又恢复判定）这些都是跨批、可级联、非局部的。增量重算要为每一类边界维护正确的失效传播，任何一处漏掉都会产生静默的状态分叉。
2. **一致性是硬需求、性能是可优化项。** “逐字段等于从头重放”本身就是正确性判据；直接执行该判据，使存储层不可能偏离它，测试也可以直接拿“独立重放”做逐字段断言。
3. **代价清晰、可控。** 代价是 O(L) 的重放 + O(L) 的派生行重写（L=批次数）。一台普通实例上，数千批 / 次写入是亚毫秒到毫秒级；若将来单流达到数万、数十万批，再引入检查点（按时间分段存 State 快照，定位到受影响批次之前最近的检查点继续），且检查点同样由“重放生成、重放校验”，不改变正确性模型。当前不提前引入这层复杂度。

**并发**：每个写事务先取该流的 PostgreSQL 事务级咨询锁（`pg_advisory_xact_lock`，键由流 id 哈希）。同一流的并发录入 / 补录因此串行化，配合唯一约束 `(stream_id, seq)` 与 `(stream_id, batch_id)`，不会丢批、不会重复计分、不会状态交错；咨询锁键随流不同，**不同流之间互不阻塞**。并发压测（16 协程 × 60 批）后核对：事件数、seq 无缺号无重复、派生结果数=事件数、最终状态与独立重放逐字段一致。

## 6. HTTP 接口（前缀 `/api/v1`）

### 方案档

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/plans` | 新建（同时生成覆盖全部历史的修订 1） |

| POST | `/plans/{id}/revisions` | **追加修订**：body 同建/改档，外加可选 `effective_at`（RFC3339；省略=即刻生效，可将来可补记到过去）。返回新修订号、生效时刻与各绑定流差异 `diff` |
| GET | `/plans/{id}/revisions` | 修订历史（按生效时刻、修订号排序） |
| GET | `/plans/{id}/revisions/{no}` | 取指定修订；修订号不存在 → 404（号格式非法 → 400） |
| POST | `/plans/{id}/evaluate` | 给定 `p[]` 算 Pa（二次带 ASN；带 N 带 AOQ/ATI） |
| POST | `/plans/{id}/curve` | OC 等曲线，`p_min/p_max/points`（points ≤ 500） |
| POST | `/plans/{id}/risks` | `{aql, ltpd}` → α、β、Pa(AQL)、Pa(LTPD) |
| POST | `/plans/{id}/aoql` | AOQL 及对应 p（需带 N） |

一次档 body：

```json
{ "name": "n80c2", "kind": "single",
  "single": { "n": 80, "c": 2, "n_lot": 1000, "distribution": "hypergeometric" } }
```

二次档 body（约束 `c1 < r1 ≤ c2+1`，`r1` 可取 `n1+1` 表示一阶段不直接拒收）：

```json
{ "name": "dbl", "kind": "double",
  "double": { "n1": 50, "c1": 2, "r1": 5, "n2": 50, "c2": 6 } }
```

### 反向设计

- `POST /design/single`：`{aql, alpha, ltpd, beta, n_lot?, distribution?, n_max?}`
- `POST /design/double`：同上加 `n2_mode: "equal"|"twice"`、`n1_max`
- 超上限无可行方案 → `404` 且错误信息明确说明。

### 检验流

| PUT | `/streams/{id}/batches/{batch_id}` | 修正批号 / 时间 / 不合格数（保留原 seq） |
| DELETE | `/streams/{id}/batches/{batch_id}` | 删除一批 |
| POST | `/streams/{id}/flags` | `{flag:"stable"|"approved", value, at?}` |
| POST | `/streams/{id}/resume` | 暂停后人工恢复 |

批次 body：`{"batch_id"?: "...", "lot_no": "...", "inspected_at"?: RFC3339, "d1": 3, "d2"?: 2}`。
二次抽样当 `c1 < d1 < r1` 时必须给 `d2`。

### 校验与错误

`n<1`、`c<0`、`c≥n`、`p∉[0,1]`、`N<n`、`AQL≥LTPD`、`α/β∉(0,1)`、不合格数超过该批检验时刻生效修订的样本量等一律 `400`，响应形如：

```json
{ "error": "validation error",
  "fields": [ { "field": "single.c", "message": "must satisfy c < n" } ] }
```

修订相关：

- 修订号不存在 → `404`；修订号格式非法 → `400`（字段 `revision_no`）。
- `effective_at` 不是 RFC3339 → `400`（字段 `effective_at`）；修订参数不合法（如 `c≥n`）→ `400`（字段 `single.c` 等）；修订试图改变抽样 `kind`（single↔double）→ `400`（字段 `kind`）。
- 修订让已录批次无法判定 → `422`，`conflicts` 逐批点名：

```json
{ "error": "revision rejected: recorded batch(es) cannot be judged under it",
  "conflicts": [
    { "batch_id": "c", "lot_no": "C", "inspected_at": "2026-03-03T00:00:00Z",
      "severity": "normal", "plan_id": "…", "revision_no": 3,
      "reason": "d1: defect count must be within [0, first sample size]" } ] }
```
